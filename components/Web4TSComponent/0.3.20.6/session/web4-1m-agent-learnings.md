## 1. Architectural Eras

Web4TSComponent evolved through 5 distinct eras. Components generated in one era may not work with Web4TSComponent from another era.

### Era 1: Pre-Completion (≤ 0.3.5.x) — 41 methods
- **Reference implementation:** PDCA 0.3.5.2
- No DelegationProxy — each component is self-contained
- Individual symlink methods: `setDev()`, `setTest()`, `setProd()`, `setLatest()`
- Version discovered from directory structure (not hardcoded)
- DefaultCLI has `initWithComponentClass()` pattern
- CLI entry: `static async start(args)` → `new CLI()` → `execute(args)`
- TSCompletion exists but no `actionParameterCompletion` or `shCompletion`

### Era 2: Enhanced Completion (0.3.18.x) — 68 methods
- Unified `setCICDVersion(targetVersion)` replaces individual set methods
- `shCompletion()`, `completeParameter()`, `completion()` added
- `cliSignature()`, `getContext()`, `on()` method chaining added
- Tab completion with parameter discovery via `*ParameterCompletion()` methods
- Still NO DelegationProxy — components need explicit delegation methods

### Era 3: DelegationProxy (0.3.19.x) — 70 methods — **PROD STABLE**
- **DelegationProxy introduced in 0.3.19.0** — the biggest architectural change
- Generated components get 120+ methods with ZERO boilerplate
- `hasDelegation()`, `getDelegationTarget()`, `getWeb4TSComponent()`, `setTarget()` added
- Component knows only its own 3-6 methods; proxy handles the rest at call-time
- `links fix` fully implemented with `verifyScriptsSymlinks()`, `verifyLatestSymlink()`, `verifySemanticLinks()`, `fixSemanticLinks()`
- Prod version: **0.3.19.1** (UpDown), test: 0.3.19.3

### Era 4: UpDown Extensions (0.3.20.x) — 75 methods
- `tootsie()` — Radical OOP test runner (Tootsie replaces Vitest for component testing)
- `componentDescriptorUpdate()`, `componentDescriptorRead()`, `componentStart()` added
- `testShell()` for isolated test environments
- `updateBuildSystem()` still available
- Current dev/latest: **0.3.20.6**

### Era 5: ONCE Embedding (0.3.22.x) — ~45 methods + 15 ONCE-specific
- Web4TSComponent absorbed into ONCE as `@web4x/once` npm package
- ~30 scaffolding methods removed (create, scaffoldComponent, initProject, etc.)
- ONCE-specific methods added: `peerStart/Stop`, `startServer`, `demo`, `unitsDiscover`, `openBrowser`
- **REGRESSION:** `links fix` gutted — `action` parameter accepted but ignored
- **REGRESSION:** `verifyScriptsSymlinks()` and 4 related verify/fix methods completely removed
- Web4TSComponentCLI.ts is now a thin wrapper importing from `@web4x/once`
- ONCE 0.3.22.2's `DefaultWeb4TSComponent.ts` is the actual source

| Pre-delegation | ≤ 0.3.18.x | PDCA 0.3.5.2, 0.3.6.x | Anything expecting DelegationProxy |
| DelegationProxy | 0.3.19.x | Components generated by 0.3.19.x | Pre-delegation components that need explicit delegation |

| ONCE embedded | 0.3.22.x | ONCE 0.3.22.x only | Standalone components expecting full Web4TSComponent |

**Rule:** Use the prod version of Web4TSComponent that corresponds to the component's generation era.

## 3. PDCA 0.3.5.2 — The Reference Implementation

Why PDCA 0.3.5.2 is the best-implemented component:

1. **Self-contained architecture:**
   - `DefaultPDCA.ts` (203.9KB) — full business logic
   - `DefaultCLI.ts` (85.2KB) — complete CLI infrastructure
   - `TSCompletion.ts` (38.4KB) — TypeScript completion engine
   - No external @web4x dependencies

2. **Version discovery pattern (no hardcoded versions):**
   ```typescript
   // PDCACLI.ts — discovers version from directory structure
   const tempComponent = new DefaultPDCA();
   const version = (tempComponent as any).model.version;
   this.initWithComponentClass(DefaultPDCA, 'PDCA', version);

   // DefaultPDCA constructor — reads from filesystem
   const currentVersionDir = dirname(dirname(dirname(currentFileUrl.pathname)));
   const componentDirName = currentVersionDir.split('/').pop() || '0.3.4.2';
   const discoveredVersion = /^\d+\.\d+\.\d+\.\d+$/.test(componentDirName) ? componentDirName : '0.3.4.2';
   ```

3. **trainAI curriculum** — 7 topics:
   - Radical OOP (100% model-driven, this.model everywhere)
   - Functional vs OOP (why functional fails)
   - CMM3 Verification (reproducible testing)
   - Test-First development
   - Bash Completion (DISPLAY: and WORD: protocol)
   - Output Filtering (why it's forbidden)
   - Error Handling

4. **Clean 5-layer architecture:**
   - Layer 2: DefaultPDCA, DefaultCLI (implementation)
   - Layer 3: 10 interface files (contracts)
   - Layer 4: TSCompletion, Colors, HierarchicalCompletionFilter, TestFileParser (orchestration)
   - Layer 5: PDCACLI (entry point)

5. **Tests use real code** (not fake types) — pdca.test.ts, pdca.trainai.test.ts, pdca.movefile.test.ts, pdca.duallink.test.ts

## 5. Version Promotion Rules

1. **Always use `latest` symlink** — never hardcoded version numbers
2. **`upgrade` creates a new version** and moves `latest` — does NOT touch dev/test/prod
3. **`setCICDVersion`** moves stage symlinks (dev/test/prod) — separate from upgrade
4. **Prod must be stable** — only promote after 100% test pass
5. **Components should use the prod version** of Web4TSComponent that matches their era
6. **Direct CLI scripts** from `scripts/` are preferred over `web4tscomponent on X latest` (auto-build vs pre-compiled JS)

## 7. Web4 Patterns Quick Reference

| Pattern | Rule |
|---------|------|
| **Radical OOP** | `this.model` everywhere, zero parameters to helper methods |
| **Empty Constructor** | `constructor() {}` + `init(scenario)` |
| **Method chaining** | All methods return `this` (or `Promise<this>`) |
| **No flags** | Positional parameters only, no `--help` or `-v` |
| **Self-explaining** | Run with no args = usage display |
| **Tab discovers** | Tab completion discovers all methods |
| **ISR** | IOR Self-Replacement: strings → IOR objects → instances (lazy load) |
| **Guard pattern** | `if (!this.guardReady()) return this;` — never block, never throw |
| **JsInterface** | Runtime interface via abstract class extending JsInterface (P35) |
| **5-Layer Architecture** | L1: Infrastructure, L2: Implementation, L3: Interfaces, L4: Orchestration (async), L5: UX/CLI |
| **nameVerb naming** | `componentDescriptorUpdate()` not `updateComponentDescriptor()` |
| **Path Authority** | CLI calculates `projectRoot` once, components use accessors |
| **No factory functions** | Always `new Class().init(scenario)` |
| **DRY fetch** | All resource access via IOR, never raw `fetch()` (except SW) |

## 8. Hands-On Discoveries (2026-03-20)

### Discovery 1: `links fix` auto-promotes prod — DANGEROUS

Running `web4tscomponent on <component> latest links fix` forces prod to point to the highest available version. This is wrong — prod should only be promoted intentionally after 100% test success.

**Observed:**
- Unit: prod 0.3.0.5 → auto-promoted to 0.3.19.1
- PDCA: prod 0.3.20.0 → auto-promoted to 0.3.20.1

**Root cause:** `fixSemanticLinks()` in prod (0.3.19.3) line 1328 uses policy "all semantic links point to highest version by default". This is wrong for prod. Prod represents the last known-stable version and should NEVER be auto-moved.

**Manual fix applied:** Reverted both and set PDCA prod=0.3.5.2 (the best-implemented reference version, per Tron).

### Discovery 2: `links fix` does NOT create scripts/ symlinks

After running `links fix` on PDCA, `scripts/pdca` was NOT created despite `components/PDCA/latest/pdca` existing. The `verifyScriptsSymlinks()` method (which creates scripts/ entries) exists in prod 0.3.19.3 but the current `links fix` path doesn't call it for all components.

**Result:** `pdca` is not on PATH, `which pdca` fails.

### Discovery 3: `web4tscomponent on` fails for components with dots in name

`web4tscomponent on UpDown.Cards latest` fails — it constructs `DefaultUpDown.Cards.js` but the actual class uses underscore: `DefaultUpDown_Cards`. The component naming convention maps dots to underscores in class names, but the `on` command doesn't know this.

**Error:** `Component module not found: .../DefaultUpDown.Cards.js`

### Discovery 4: `web4tscomponent on` fails for framework components

`web4tscomponent on Tootsie latest` fails — it tries to load `DefaultTootsie.js` which doesn't exist. Framework components (Tootsie, Web4Test, Web4Requirement) don't have their own Default implementation in the standard layer2 path.

**Error:** `Component module not found: .../DefaultTootsie.js`

### Discovery 5: 18 of 21 components have incomplete link sets

Full audit results:

**Missing dev AND test (13 components):**
- ArchTestProd1, CardDeckManager, ComponentMigrator, GameDemoSystem, GameLogicEngine
- GameUserInterface, IdealMinimalComponent, MultiplayerServer, ProjectStatusManager
- UpDown.Cards, UpDown.Core, UpDown.Demo, UpDown.Server, UpDown.UI

**Missing prod (4 components):**
- Tootsie, User, Web4Requirement, Web4Test

**Only 3 components have complete link sets:** ONCE, PDCA, Unit, Web4TSComponent

### Discovery 6: `upgrade` with no args is dangerous

Running `web4tscomponent upgrade` (no args) defaults to `nextMinor` and immediately creates a new version. I accidentally created 0.3.21.0 this way. The command should require an explicit version promotion type.

### Discovery 7: `pdca` (latest=0.3.20.1) lost `getDualLink` and all dual link methods

`pdca getDualLink` → `Unknown command: getDualLink`. The method exists in PDCA 0.3.5.2 (prod) but is gone from 0.3.20.1 (latest). This is a major regression — the dual link toolkit was one of PDCA 0.3.5.2's best features.

**Affected methods lost:** `getDualLink`, `getDualLinkRelativePath`, `ensureValidLinks`, `fixDualLinks`, `findPDCAsLinking`, `updateLinksToFile`

**Workaround:** Use version-specific script `pdca-v0.3.5.2` instead of `pdca`.

### Discovery 8: `pdca.prod` variant doesn't load prod version

`pdca.prod getDualLink` → still loads 0.3.20.1 source.env (latest), not 0.3.5.2 (prod). The `.prod` suffix variant doesn't work — same as BUG-W1 (completion broken on `.prod`/`.test` variants).

### Discovery 9: `getDualLink` crashes on git push failure

`pdca-v0.3.5.2 getDualLink <file>` auto-commits and auto-pushes. When push is rejected (remote ahead), the command crashes and NEVER outputs the actual dual link. The link generation should succeed regardless of push status.

### Discovery 10: `pdca-v0.3.5.2` tools work correctly

Once using the version-specific script, the dual link tools work:
- `getDualLinkRelativePath` correctly calculates relative paths
- `fixDualLinks` validates dual links inside a file
- `ensureValidLinks` scans project for PDCAs referencing a file

**Key lesson:** Always use `pdca-v0.3.5.2` for dual link operations, never `pdca` (latest).

### Discovery 11: Staging variant completions not registered (BUG-W17)

`source.env` `_web4_auto_register_completions()` only registers:
- Main scripts (`scripts/componentname`) if symlink matches `components/X/latest` and has `TSCompletion.ts`
- Versioned scripts (`scripts/versions/component-vX.Y.Z.W`) if pattern matches `-v\d+\.\d+\.\d+\.\d+`

It does NOT register:
- `.prod`/`.test`/`.dev` staging variants (pattern `component.prod`)
- Main scripts missing `TSCompletion.ts` (like `pdca` — no TSCompletion in PDCA latest)

**Fix needed in `source.env` line ~165:** Add a third loop for staging variants:
```bash
# Register staging variants (.prod, .test, .dev)
for cli in "$scripts/versions"/*.{prod,test,dev}; do
    [ -x "$cli" ] && [ ! -d "$cli" ] || continue
    local name=$(basename "$cli")
    complete -F _web4_generic_completion -o nospace "$name"
    registered+=("$name")
done
```

### Discovery 12: Staging variant symlinks out of sync with component links (BUG-W18)

`scripts/versions/pdca.prod` pointed to `pdca-v0.3.20.1` but component `PDCA/prod` was 0.3.5.2.
`scripts/versions/once.prod` pointed to `once-v0.3.21.5` but component `ONCE/prod` was 0.3.22.1.
`scripts/versions/unit.prod` pointed to `unit-v0.3.19.1` but component `Unit/prod` was 0.3.0.5.

These staging symlinks are set by `links fix` or `upgrade` but never re-synced when component links change manually. There's no tool to sync them.

**Manual fix applied:** All staging variants now match component links.

### Discovery 13: `pdca` main script not registered for completion (BUG-W19)

`complete -p | grep " pdca$"` → empty. The auto-registration in `source.env` requires `TSCompletion.ts` in `components/PDCA/latest/src/ts/layer4/`, but PDCA 0.3.20.1 uses a different completion path. Only `unit`, `once`, `web4tscomponent` get registered.

**Manual fix:** `complete -o nospace -F _web4_generic_completion pdca`

### Phase 1 Blocker: BUG-W20

`web4tscomponent-v0.3.22.4 links` returns `WORD: __CALLBACK__:actionParameterCompletion` instead of executing. The CLI's `executeDynamicCommandWithChaining()` sees the `action` parameter has a completion callback and returns it instead of calling the method with 0 args. Optional parameters with callbacks must still allow execution without the arg.

**Location:** `Web4TSComponent/0.3.22.4/src/ts/layer5/Web4TSComponentCLI.ts` line ~220 — `executeDynamicCommandWithChaining()`.

**Fix applied:** Check `(p as any).required === false` from TSCompletion metadata instead of relying on `hasDefault`/`isOptional`. Web4 parameter syntax: `<param>` = required, `<?param>` = optional, `!<param>` = required but completion method is missing (! does NOT mean mandatory — it means no completion available).

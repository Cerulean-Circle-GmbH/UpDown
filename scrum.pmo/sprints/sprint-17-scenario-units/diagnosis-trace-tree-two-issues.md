# Diagnosis: /trace Tree — Two Issues (from Tron screenshots)

---

## Issue 1: Lazy-Load Deeper Fails (Tree stops at Task level)

### Symptom
Tree expands Sprint → Tasks but NOT Task → UC → Class → Method → Impl → Test.

### Root Cause: BOTH empty data AND potentially broken tree mechanism

#### Primary: Empty Data (T178 gap — CONFIRMED)

T178 was designed (`a3f31b068`) but NOT implemented. The `/api/trace/chain` JSON has:

```
✅ requirement.forwardTo.tasks[]     — populated (T160 parser works)
✅ task.forwardTo.subtasks[]          — populated (T160 parser works)
❌ task.forwardTo.useCases[]          — EMPTY (matrix parser not built)
❌ useCase.forwardTo.classes[]        — EMPTY
❌ class.forwardTo.methods[]          — EMPTY
❌ useCase.tests[]                    — EMPTY
```

The tree component receives nodes with empty `forwardTo` arrays below Task level. Even if the expand mechanism works perfectly, there are zero children to render.

**Fix:** Implement T178 — parse traceability-matrix.md to populate all 4 hops.

#### Secondary: Tree Lazy-Load Mechanism (may also be broken)

Cannot confirm from this branch (rb-object-item / rb-tree-item components are on robbinTeam branch). But the question is: **does rb-object-item check `node.forwardTo` for children, or does it try to fetch them lazily from `/api/trace/children?uuid=X`?**

Two possible implementations:

**Design A (pre-loaded tree):** `/api/trace/chain` returns the ENTIRE tree. rb-object-item reads `node.forwardTo.useCases[]` directly. If empty → no expand arrow shown. This is what T158 design specifies.

**Design B (lazy-load):** `/api/trace/chain` returns only top-level. rb-object-item fetches children on expand via a separate API call. If that API doesn't exist or returns empty → expand shows nothing.

**Diagnosis for expert:** Check rb-object-item.ts:
```
If it reads node.forwardTo directly → Issue is purely T178 (empty data)
If it calls fetch('/api/trace/children') → ALSO need the lazy-load endpoint
```

**Likely verdict:** Design A (pre-loaded) per T158 spec. Issue is purely T178 empty data.

## Issue 2: Back-Ref Display Violation (Task shows "requirements" link)

### Symptom
T100 Task DetailView shows a "requirements" link — Task → Requirement = BACKWARD. This violates T159 forward-only rule.

### Root Cause Analysis: THREE possible fix layers

#### Layer A: Scenario Data Still Contains Back-Ref

Despite T159 strip (T172 audit = 0 matches), the Task SCENARIO JSON in `scenarios/index/` may still contain a `requirements` field:

```json
{
  "model": {
    "uuid": "...",
    "name": "Task 100",
    "requirements": ["uuid-of-req-1"]  // ← STILL IN DATA despite T172 strip
  }
}
```

T172 audited `scrum.pmo/sprints/*/task-*.md` files (markdown). But the SCENARIO JSON files in `scenarios/index/` are generated by a different path (ScenarioService/UcpStorage). **T172 may have stripped markdown but NOT scenario JSON.**

**Diagnosis for expert:**
```bash
grep -r '"requirements"' scenarios/index/ | head -5
```
If matches found → scenario data still has back-refs → strip from scenario JSON too.

#### Layer B: rb-task-detail Derives a Reverse Link

Even if scenario data is clean, the DetailView component may COMPUTE the reverse link:

```typescript
// rb-task-detail.ts (hypothetical)
renderRequirements() {
  // WRONG: scanning all requirements to find ones pointing to this task
  const parentReqs = this.allRequirements.filter(r => 
    r.forwardTo.tasks.some(t => t.uuid === this.task.uuid)
  );
  return html`<div>Requirements: ${parentReqs.map(r => r.name)}</div>`;
}
```

This is a DISPLAY violation — the data is forward-only but the renderer derives a backward link by scanning. The renderer must NOT do this.

**Diagnosis for expert:**
```bash
grep -n 'requirement' rb-task-detail.ts
```
If the component references `requirement` at all → display violation → remove that rendering block.

#### Layer C: VerbRegistry or Chain Builder Injects Back-Refs

The `buildForwardChain()` function may be injecting convenience back-refs:

```typescript
// traceChainBuilder.ts (hypothetical)
for (const req of requirements) {
  for (const taskLink of req.forwardTo.tasks) {
    const task = findTask(taskLink);
    task.requirements = task.requirements || [];
    task.requirements.push(req);  // ← INJECTING BACK-REF
  }
}
```

**Diagnosis for expert:**
```bash
grep -n 'requirement' traceChainBuilder.ts
```
If the builder adds a `requirements` field to TaskNode → it's creating back-refs → remove.

### Fix Layer Summary

| Layer | What to check | Fix |
|---|---|---|
| **A: Data** | `grep '"requirements"' scenarios/index/` | Strip from scenario JSON |
| **B: Renderer** | `grep 'requirement' rb-task-detail.ts` | Remove backward render block |
| **C: Builder** | `grep 'requirement' traceChainBuilder.ts` | Remove back-ref injection |

**All three layers must be clean.** T159 says forward-only at every level: data, builder, renderer.

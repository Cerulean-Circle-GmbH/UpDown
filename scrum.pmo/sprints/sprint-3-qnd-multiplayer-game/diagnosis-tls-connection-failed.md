# CRITICAL DIAGNOSIS: Tron's Device — v0.2.12 + 'Connection Failed' / 'You're Offline'

**Reported by:** Tron (iPhone, real Safari, home.donges.it)
**Root cause:** Self-signed cert CN=localhost served to home.donges.it — iOS Safari rejects it silently for wss://

---

## (1) TLS Certificate Analysis

### Current cert
```
Issuer:  CN=localhost
Subject: CN=localhost
Type:    Self-signed (no CA)
Version: v1 (no SAN extension)
Expires: 2026-11-28
Generated by: openssl req -x509 ... -subj "/CN=localhost"
```

### What iOS Safari does with this cert

**HTTPS (port 443/8443):**
- Safari shows "This Connection Is Not Private" warning
- User CAN tap "Show Details" → "Visit This Website" to bypass
- After bypass, HTTPS works for that session
- BUT: the bypass is per-hostname. CN=localhost ≠ home.donges.it → Safari rejects because the CN doesn't match the accessed hostname

**WSS (WebSocket over TLS):**
- **There is NO "proceed anyway" for WebSocket connections**
- Safari establishes the TLS handshake for wss:// silently
- If cert validation fails (CN mismatch, self-signed, expired), the connection is **silently dropped**
- The WebSocket `onerror` fires → client shows "Connection Failed"
- User has NO way to bypass this — no interstitial, no button, just failure

### The chain of failure on Tron's device

```
1. iPhone opens https://home.donges.it:8443
2. Server presents cert CN=localhost
3. Safari warns "Not Private" — Tron taps proceed
4. HTML/JS loads (HTTPS bypass worked for the page load)
5. JavaScript opens wss://home.donges.it:8443
6. Safari does TLS handshake for WebSocket
7. Cert CN=localhost ≠ home.donges.it → VALIDATION FAILS
8. WebSocket silently rejected — no bypass possible
9. onerror fires → "Connection Failed" / "You're Offline"
```

**This is why our tests never caught it:** `--ignore-certificate-errors` bypasses validation for BOTH HTTPS and WSS. Real Safari has no equivalent flag.

## (2) What It Takes for a Real Browser to Connect

### Option A: mkcert (development — LAN only)

```bash
# Install mkcert
brew install mkcert
mkcert -install  # Installs local CA into system trust store

# Generate cert for home.donges.it
mkcert home.donges.it localhost 127.0.0.1 ::1

# Produces:
#   home.donges.it+3.pem      (cert with SAN for all 4 names)
#   home.donges.it+3-key.pem  (private key)
```

**Pros:** Works immediately on the Mac. iOS requires installing the mkcert CA profile via Safari (navigate to the CA cert URL, install profile, enable full trust in Settings → General → About → Certificate Trust Settings).

**Cons:** Every device on the LAN needs the CA profile installed. Not suitable for public access.

### Option B: Let's Encrypt (production — public domain)

```bash
# Requires: home.donges.it DNS pointing to server IP, port 80 open for ACME challenge
certbot certonly --standalone -d home.donges.it
# or with DNS challenge if port 80 not available
```

**Pros:** Universally trusted. All browsers, all devices, zero config on client side.

**Cons:** Needs public DNS + port 80/443 accessible from internet. Auto-renewal needed (90-day certs). Already designed in @web4x/tls (LetsEncryptCertificateProvider, CertificateRenewalScheduler, ACMEChallengeRoute).

### Option C: Self-signed with correct SAN (quick fix — still shows warning)

```bash
openssl req -x509 -newkey rsa:2048 -nodes -sha256 -days 365 \
  -keyout key.pem -out cert.pem \
  -subj "/CN=home.donges.it" \
  -addext "subjectAltName=DNS:home.donges.it,DNS:localhost,IP:127.0.0.1"
```

**This fixes the CN mismatch** but Safari still warns (self-signed). The HTTPS bypass works, but **WSS still fails** on iOS Safari because the WebSocket TLS handshake doesn't inherit the page-level bypass.

**Verdict: Option C does NOT fix the WSS problem on iOS.** Only Options A or B work.

## (3) Stale Service Worker Upgrade Path

### Current state on Tron's device
- SW version: v0.2.12 (cached months ago)
- Current server version: v0.5.78
- SW controls all fetches → serves stale cached assets
- SW precache list references old file hashes

### What happens when Tron loads the page

```
1. Browser loads cached v0.2.12 SW (from SW storage — not network)
2. SW intercepts ALL fetches (HTML, JS, CSS, API calls)
3. SW serves cached v0.2.12 assets
4. Browser checks for SW update in background
5. Fetches /sw.js from server → gets v0.5.78 SW source
6. BUT: fetch goes through HTTPS → cert validation → FAILS (CN mismatch)
7. SW update fetch fails silently
8. Old SW v0.2.12 remains active
9. Even if user "clears cache" — SW is NOT cleared by normal cache clear
10. SW persists until: (a) unregister via DevTools, or (b) /sw.js fetch succeeds with valid cert
```

### The cert blocks the SW upgrade

Even if we fix everything else, the SW update mechanism itself uses HTTPS fetch. If the cert is invalid, the browser won't fetch the new SW. The old SW stays forever.

### Fix sequence (must be in this order)

```
Step 1: Deploy valid cert (mkcert or Let's Encrypt)
  → HTTPS + WSS both work on real browsers

Step 2: Server serves new /sw.js with v0.5.78
  → Browser background-checks /sw.js
  → Valid cert → fetch succeeds → new SW installed
  → New SW activates on next navigation

Step 3: New SW precaches current asset hashes
  → Old v0.2.12 assets replaced

Step 4: WebSocket connects via wss:// with valid cert
  → "Connection Failed" / "You're Offline" resolved
```

**If step 1 is skipped, steps 2-4 all fail.** The cert is the keystone.
